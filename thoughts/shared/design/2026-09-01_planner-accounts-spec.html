Students, not
just accounts

A plan belongs to a student, not to a login. Once the planner knows what grade that student is in, half the interface gets smarter — and the scariest screen in the last revision mostly disappears.

White screens — the live site, real tokens Blue — new, proposed Amber — the share-link fix Screens stay light in both themes — the site is light-only
RULE 01

No forced login. Every feature works signed out, forever.

RULE 02

Plans belong to students. An account holds students; a student holds a plan.

RULE 03

Accounts add sync, nothing else. Grade, locks and second students all work signed out.

RULE 04

Ask at the right moment. Never on arrival — only once there's work worth losing.

RULE 05

Nothing is destroyed silently. Merges add; they never overwrite.

Part A

The student model

Three changes that need no account at all: knowing who the plan is for, what grade they're in, and which courses are already settled. This is the half that makes the planner better for everyone, signed in or not.

A1

Appears the first time someone opens the planner. Skippable, changeable later, and answered by tapping a number. We store the graduation year rather than the grade, so it never goes stale in August.

One flag, not four states

Completed comes free from grade level. The only thing worth storing is confirmed — a single boolean per course.

What the lock actually does

Autofill skips it, "Clear all" spares it, and removing it takes a second tap. It protects against machinery, not against you.

Naming

"Locked" describes the mechanism; "Confirmed" describes the student's world. Label it Confirmed, draw it as a lock.

The stored shape — identical in localStorage and in the account { schema: 2, activeStudent: "s1", students: [ { id: "s1", label: "Zavien", // optional, defaults to "Student 1" classOf: 2029, // grade is derived from this + today plan: { 9: [ { c: "1101H" }, { c: "2203H" } ], 10: [ { c: "1102H", confirmed: true } ], 11: [], 12: [] } } ] } Migration: today's plan is { 9: ["eng-9-h", ...] } — bare strings, no students. A v1 blob is read as one unnamed student with no classOf, so nobody loses a plan. ~500 bytes per student against Clerk's 8KB cap: room for a dozen students.
Part B

Accounts, which only sync

Everything above already works without signing in. An account does exactly one thing: it carries those students to the next device. Which turns out to make the hardest screen from the last revision much softer.

B1

The icon is the entire permanent signed-out footprint. The bar appears on the fourth course added, never on arrival, and dismissing it is permanent.

Build order

1 · Share-link fix. B5, standalone. Live data-loss bug, no auth, no student model.

2 · Print / PDF. Independent, cheap, serves the counsellor meeting.

3 · Student model. A1–A4 plus the schema-2 migration. All of it works signed out.

4 · Accounts. B1–B4, B6. Google first, Apple after.

What this costs

A schema migration. Courses go from bare strings to objects, and plans gain a student wrapper. Backward-compatible read, so nobody loses work — but it has to be written carefully and tested against a v1 blob.

Grade-aware logic touches the credit calculator, the warnings, the empty states and the wizard.

Still open

Student names are new PII. Today the site stores no names. Optional labels change that, and the privacy policy needs rewriting before this ships, not after.

A cap on students. Unbounded lets a sync loop fill an account. Four or five is more than any family needs.

Does the wizard become per-student? It writes a whole plan, so it needs to know which student it's writing for.
